# gemfire-application-config

Source of truth for **application-level** Apache Geode configuration. One shared `values.yaml` per application/environment.
Deployment implementation (Helm chart, pipelines, scripts) lives in `gemfire-k8s-helm`.

## Layout

```text
<application>/<environment>/values.yaml     e.g. ecom/dev/values.yaml
schemas/application-config.schema.json     JSON Schema for every values.yaml
```

Currently defined (demo): **only `ecom/dev`**, deployed as `ecom-dev-dr` first, then `ecom-dev-primary`.

## Adding a new application or environment (no CI/CD or chart change)

1. Create `<app>/<env>/values.yaml` (copy `ecom/dev/values.yaml`, change `application.name` / `environment`).
   - `<app>`: lower-case, 2-16 chars (`swp`, `b2c`, ...). `<env>`: `prod`, `dev`, `stg` or `qa`.
2. Open a PR. The pipeline detects any new `<app>/<env>/values.yaml` path by pattern (no list to update),
   validates it, and deploys that one application/environment to DR first, then Primary after approval.
3. Nothing else is touched: other folders are never redeployed.

## Core rules

1. **One file, both sites.** Primary and DR consume the same file at the same commit. There is no Primary or DR variant.
2. **No site identity here.** `distributed-system-id`, locators, remote-locators, endpoints and certificates are generated by `gemfire-k8s-helm`. IDs are `ENV x 10 + SITE` (prod=1, dev=2, stg=3, qa=4; primary=1, dr=2), so `ecom-dev-primary` = 21 and `ecom-dev-dr` = 22.
3. **No secrets** in this repo.
4. **Naming:** folder names equal `application.name` and `application.environment`. Region names are UPPER_SNAKE_CASE.
5. **DEV may differ from PROD** in sizing; Primary and DR never differ from each other.
6. **Demo sizing:** small on purpose (2 servers, 1 locator, 5Gi per server). Increase only when you have a reason.

## Change flow

PR -> validation -> merge -> pipeline detects the changed path -> deploy DR -> verify DR -> approval -> deploy Primary from the recorded commit -> verify Primary and WAN.
